# 0034 — Crash retries are immediate, and Com ignores released messages

| | |
|---|---|
| **Status** | blocked |
| **Module** | Prime / Com |
| **Platform** | AWS Lambda |
| **First seen** | 2026-11-24 |
| **Milestone** | A3 — Integration |

## Description

Follow-ups from the #0033 review, none blocking.

- **Crash backoff:** Prime's crash path releases and self-wakes at once, so a short S3 outage can exhaust `maxReceiveCount` (5) in seconds and send good messages to the DLQ. Consider a 30–60 s backoff.
- **Com ignores `stop().released`:** a request acked between its final poll and `stop()` (a few ms) is released, but nobody wakes Com. Not a regression.
- **Worker death:** Prime's `stop()` rejects and sends no self-wake, so messages wait out the 900 s visibility timeout.
- **Docs:** protocol §9E and spec §5.4–5.5 don't describe release and self-wake; spec line 250 still says the token is an environment variable.

## Relation

Follow-up to #0033, #0032.

## Progress

`1937430`: Com goes round again when `stop()` released something (reviewed: APPROVE, no regression). **Limit:** Prime's requests have a 600 s timeout, so after 240 s of Com run time a second pass declines the request and the old race (a few ms) remains. Found by reading, not reproduced. A full fix needs Com to be able to wake itself.

## Blocked

Owner decisions: (1) add a 30–60 s crash backoff for Prime, or accept immediate retries; (2) grant Com a self-invoke, or accept the remaining race; (3) approve edits to `docs/spec.md` and `docs/protocol.md`.

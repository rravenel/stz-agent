## Description

`CommsCore.stop()` lets the in-flight long poll finish, and `handle()` still **acks** and delivers whatever that poll returns, even though the consumer is shutting down. `WorkerComms` likewise forwards worker deliveries to the main-thread handler after `stop()` was called. The sender sees the ack and stops waking; the message is never deleted, stays invisible for the queue's visibility timeout (Prime: 900 s), and nothing processes it. There is also no way for a consumer to hand a received message back. This is the Track A half of Track B's #0029, and it is what made rene's #0023 run fail (2026-11-21 02:42 UTC: prewake → Prime `stale_wake` after 1 s → `POST /messages` got 202 → no further Prime run for 600 s).

## Root cause

- `functions/shared/src/comms-core.ts` `stop()` sets `stopped`, then `await this.polling`; `pollOnce` → `handle()` does `enqueue(makeAck(msg))` and calls the handler regardless of `stopped`.
- The ack tells the sender "I'm awake and I have it" (protocol §6) while the owner is exiting, which breaks positive handoff (spec §3 rule 3). The sender's monitor clears the entry, so no later wake comes (protocol §9B's recovery depends on the message staying **unacked**).
- `QueuePort` has `receive/send/delete` only, with no `ChangeMessageVisibility`, so undelivered work can't be made visible again.

## Plan

Files: `functions/shared/src/{comms.ts,comms-core.ts,comms-worker.ts,aws-ports.ts}` + their tests. `comms.ts` is the shared A0 contract: the change is **additive** (a new method; `stop()` resolves to a value instead of `void`), so Prime's existing `await comms.stop()` keeps compiling. Note it on #0029.

1. **`QueuePort.release(receipt)`**: `SqsQueuePort` → `ChangeMessageVisibilityCommand({ VisibilityTimeout: 0 })`. Add it to the memory ports and the test fakes. IAM: `grant_consume_messages` already includes `sqs:ChangeMessageVisibility`; add a pytest assertion that it does.
2. **No ack and no hand-off once stopping.** In `CommsCore.handle()`, if `stopped` is set and the message isn't an ack: **don't ack, don't deliver**; `release(receipt)`, log `{kind: "released", msg_id, reason: "stopping"}`. Acks are still processed (clearing unacked entries is always safe). The sender keeps responsibility and re-wakes after `WAKE_ACK_TIMEOUT` (protocol §9B: first wake 429 while this instance returns, next wake starts a fresh one).
3. **Release delivered-but-undeleted messages on stop.** Track receipts handed to the handler; `deleteMessage` removes them. `stop()` releases every receipt still tracked and resolves `{ released: number }`. A consumer that exits normally has deleted everything (Prime after checkpoint, Com on accept), so this only fires on the abandoned-inbox race. Add `release(receipt): Promise<void>` to the `Comms` interface (and `InMemoryComms`) for consumers that want to give one back explicitly.
4. **`WorkerComms`**: set `stopping` on main as soon as `stop()` is called. A `delivery` message that arrives after that is not passed to the handler; main posts `{op: "release", receipt}` back. Worker-side `stop` releases its tracked set and returns `{released}` through `done`. Add the `release` op.
5. **Tests** (fake queue + mock timers):
   - A message that arrives in the in-flight poll during `stop()` is not acked, not delivered and is visible again. The sender's monitor still has it unacked and wakes again after `wakeAckTimeout`.
   - A delivery handed to the handler but never deleted is released by `stop()`, and `released === 1`.
   - A deleted delivery is not released.
   - Acks during stop still clear entries.
   - `WorkerComms` in `mode: "memory"`: a delivery that races `stop()` is released, not handed to the handler.
   - The #0029 scenario end to end with `CommsCore` + fakes: stale-wake style stop → the message gets no ack → a second consumer started later receives it.
6. **Verify**: with the usual exports, `scripts/check.sh` → `CHECK OK`.
7. **Track B follow-up (#0029, after this lands):** Prime's handler, on every exit path, checks `(await comms.stop()).released > 0` and, if so, sends `selfWake({reason: "continue"})` before returning. Those messages were acked (they reached the handler), so their senders won't wake Prime again. Steps 2 and 3 cover the rest.

## Expected behavior

Done when: `scripts/check.sh` → `CHECK OK`; a message that reaches a stopping consumer is never acked-and-stranded; `stop()` reports and releases anything it handed off but nobody deleted.

## Decisions taken without the owner

- `WorkerComms` drops a delivery that races `stop()` instead of posting a release: the worker tracks it, and its `stop()` releases and counts it.
- Both halves (this and the #0029 Prime follow-up) landed in one commit, to leave no window where messages strand.
- Prime also wakes itself on the crash path. **Wants owner feedback:** retries are immediate, so a short outage can use up `maxReceiveCount` (5) in seconds and send messages to the DLQ (#0034).

## Description

Prime's scale-to-zero story depends on snapshotting a QuickJS-in-WASM instance and restoring it in a fresh process, mid-await. Prove it in plain Node first, measure it, and pick the runtime build, or switch to the replay fallback by about 1:30 into the hackathon.

## Long Description

Spec §5.2, §10 S1; open-questions risk 1:
- Work under `spikes/s1-quickjs/` (Track B's own folder; plain Node script plus a vitest file so `scripts/test.sh` can run it if it's wired into a package).
- Candidates: quickjs-emscripten **sync** build (never Asyncify) or a QuickJS WASI build under Node's `WebAssembly`/WASI. Emscripten glue keeps state outside linear memory (stack pointer, FS), the likely snag.
- Checks, each in a **new process** after restore:
  1. Variables and functions defined before the snapshot are still there.
  2. A promise pending before the snapshot resolves after restore when the host resolves `__pending[id]`.
  3. Host functions still work when re-registered in the same order.
  4. Snapshot size and restore time (report numbers).
- Then the same in Lambda: **Needs owner:** deploy a test function and run it (agents have no AWS credentials).
- Decision recorded in the issue and in `docs/spec.md` §5.2: chosen build, or the replay fallback (re-run logged evals in order, serving `fetch` from logged responses).

## Decisions taken without the owner

- **Build: quickjs-ng v0.18.0 `qjs-wasi-reactor.wasm`** (the official release asset, pinned by SHA-256) instead of quickjs-emscripten. The reactor exports the QuickJS C API and imports only WASI, so the whole interpreter state is in linear memory. Emscripten keeps glue state outside it, and its npm packages can't be reached from the agent sandbox.
- **Own minimal WASI shim, not `node:wasi`**: clocks and stdout only, no files or env. Restoring must not call `_initialize`, which `node:wasi` insists on, and the shim exposes nothing on the host.
- **Host functions are wasm-table trampolines** appended in a fixed order. `restore` refuses a different order.
- **The spike stays out of `scripts/check.sh`**, because it downloads the wasm. Run it with `spikes/s1-quickjs/run.sh`. **Wants owner feedback:** should Prime vendor the wasm in git (1.5 MB) or fetch it at build time like the spike does?

## Root cause

Prime's scale-to-zero design depended on a QuickJS snapshot/restore that hadn't been tried yet (spec §5.2, open-questions risk 1).

## Fix

`spikes/s1-quickjs/`: `quickjs.ts` (boot, eval, run jobs, snapshot, restore), `harness.ts` (Prime-style host functions and `__pending`/`__evals` prelude), `child.ts` (restore and checks in a new process), `s1.test.ts`, `run.sh` and `fetch-wasm.sh`. The results are in `spikes/s1-quickjs/README.md` and in spec §5.2. **No replay fallback needed.**

## Verification

`spikes/s1-quickjs/run.sh` → `ok s1-fetch-wasm`, `ok s1-spike … ℹ pass 5`:
1. Variables and functions survive a restore in a new process (`greet`, `let counter`, `var notes`).
2. An eval suspended in `await fetch()` at snapshot time resolves after restore → `{status:"done", value:"hello world 42"}`.
3. Host functions work after re-registration in the same order; the request counter continues (`r2`).
4. Linear memory 2,424,832 bytes; snapshot (gzip -1) ~120 KB; snapshot ~20–25 ms; restore in a new process ~20–40 ms (M4, Node 26).

Also passing: a different host-function order is refused; one snapshot gives independent instances; the CPU-limit interrupt works before and after restore.

**Not run: the Lambda half of S1.** **Needs owner:** deploy a test function running `child.ts` against a snapshot (AWS credentials). Track A's stack (#0003) can host it.

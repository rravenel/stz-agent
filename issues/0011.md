## Description

Prime's scale-to-zero story depends on snapshotting a QuickJS-in-WASM instance and restoring it in a fresh process, mid-await. Prove it in plain Node first, measure it, and pick the runtime build, or switch to the replay fallback by about 1:30 into the hackathon.

## Long Description

Spec §5.2, §10 S1; open-questions risk 1:
- Work under `spikes/s1-quickjs/` (Track B's own folder; plain Node script plus a vitest file so `scripts/test.sh` can run it if it's wired into a package).
- Candidates: quickjs-emscripten **sync** build (never Asyncify) or a QuickJS WASI build under Node's `WebAssembly`/WASI. Emscripten glue keeps state outside linear memory (stack pointer, FS), the likely snag.
- Checks, each in a **new process** after restore:
  1. Variables and functions defined before the snapshot are still there.
  2. A promise pending before the snapshot resolves after restore when the host resolves `__pending[id]`.
  3. Host functions still work when re-registered in the same order.
  4. Snapshot size and restore time (report numbers).
- Then the same in Lambda: **Needs owner:** deploy a test function and run it (agents have no AWS credentials).
- Decision recorded in the issue and in `docs/spec.md` §5.2: chosen build, or the replay fallback (re-run logged evals in order, serving `fetch` from logged responses).

## Expected behavior

Done when: Spike tests pass locally via `scripts/test.sh`; the four checks and the measured numbers are recorded in the issue.

## Description

Prime can't persist itself. Implement the spec's checkpoint (`state.json`, `repl.bin`, workspace sync, then `latest.json` last), restore from the latest checkpoint, deletion of held SQS messages only after a durable checkpoint, and failing stale pending requests as `lost`.


## Root cause

#0013's checkpoint was a minimal placeholder: no workspace sync, no handling of stale pending requests, and no crash tests. Three #0013 review notes were open.

## Fix

Branch `track-b/0015-checkpoint`, commit `c55e81b`. It follows the `## Plan`.

- **`checkpoint.ts`**
  - **Save order:** `state.json`, `repl.bin`, `syncUp`, then `latest.json`, which is the commit point. A failure at any earlier step throws, and the previous checkpoint stays in effect.
  - **Load:** read `latest.json`, the state and the snapshot, then `syncDown`, then `Repl.restore`.
- **`workspace-sync.ts`**
  - **`syncUp`** walks the workspace with `lstat` and uploads only regular files whose SHA-256 changed since the last sync. It deletes keys whose files are gone and reports skipped symlinks and special files in the `checkpoint` log event.
  - **`syncDown`** empties the local dir, refuses keys that would escape it, and writes each file with `wx`, so it never follows or overwrites anything.
- **`handler.ts`:** after restore it calls `harness.failStale(now)`. Held messages are still deleted only after `saveCheckpoint` returns.
- **`loop.ts`, `failStale`:** any entry older than `timeout_s + 60` s is logged as an `error` with `lost: true` and goes through the normal failure path. For a REPL fetch, `rejectPending` turns it into the tool result; for a model call, the turn ends with the failure marker.
- **#0013 review note 1:** `/clear` calls `Repl.discard(id)` for each open tool call. The prelude drops a discarded eval's result when it settles. `Repl.evalIds()` exists for checking leaks.
- **#0013 review note 2:** `LogWriter.append` takes `fields` as a function of the seq it writes. `model.request` derives its id and `body_ref` from that seq.
- **#0013 review note 3:** REPL request ids are now `repl-<run8>-rN`.
  - **What this means after a crash:** the fetch is re-issued under a new id, so Com runs it again (spec §5.4 allows duplicates). The crashed run's late response is unknown and dropped.
  - **Why not reuse the id:** it could hand the crashed run's response to a re-issued request that isn't the same request.
- **`store.ts`:** `ObjectStore.delete`.
- **`test-world.ts`:** the test stack moved out of `loop.test.ts`, with store and comms wrappers for fault injection.

**Not done:** the optional warm-start skip (no download when memory already holds checkpoint `n == latest`). The REPL prelude change affects only new sessions.

## Gotchas

- **The workspace isn't versioned per checkpoint.** A crash after `syncUp` but before `latest.json` leaves `workspace/` one step ahead of the restored REPL. That matches spec §5.4 ("side effects may repeat").
- **Every restore downloads the whole workspace**, because the dir is emptied first. That's fine at hackathon sizes. The optional warm-start skip would avoid it.
- **Output from a discarded eval** still lands in `__io` and is attributed to the next eval that settles. This is #0012's known gotcha.
- **For #0016:** a crash between `latest.json` and the deletes is safe, because redelivered messages are deduped through `seen_msg_ids` in the saved state.

## Long Description

Spec §4, §5.4; protocol §6:
- Write order: `prime/ckpt-<n>/state.json`, `prime/ckpt-<n>/repl.bin`, sync `/tmp/workspace` → `workspace/`, **then** `prime/latest.json` `{"n": N}`. A crash in between leaves the previous checkpoint in effect.
- Restore: read `latest.json`, load state, restore the REPL snapshot, sync the workspace down. Optional: skip when memory already holds checkpoint `n == latest`.
- Held messages: deleted from SQS only after the checkpoint that includes their effects is durable.
- On restore, fail any `pending_requests` older than `timeout_s + 60 s` as `lost` (reject the REPL promise or report the model call failed); responses for unknown `request_id`s are logged and dropped.
- Unit tests with a fake S3: atomicity (crash before `latest.json`), restore round trip with a pending fetch, stale request failure, delete-after-checkpoint ordering.

## Plan

All changes are in `functions/prime/src/`.

1. **`checkpoint.ts`**
   - **`saveCheckpoint`** keeps the spec's order: `ckpt-<n>/state.json`, then `ckpt-<n>/repl.bin`, then the workspace sync up, then `latest.json`. A failure at any step throws before `latest.json` is written, so the previous checkpoint stays in effect.
   - **`loadCheckpoint`:** read `latest.json`, the state and the snapshot, then `Repl.restore`, then sync the workspace down.
2. **`workspace-sync.ts`**
   - **Up:** walk `/tmp/workspace` with `lstat` and upload regular files only. **Symlinks and other non-regular files are skipped and logged, never followed** (#0012 review). Delete `workspace/` keys whose file is gone, so deletes carry over. Upload only files whose SHA-256 differs from the manifest taken at the last sync.
   - **Down:** empty the local workspace dir, then write every `workspace/` key as a regular file. Keys with an empty, `.` or `..` segment are rejected. Emptying the dir first means a warm container can't keep a stale file or a symlink from an earlier run, and the restore never creates a link.
   - **Not done:** skipping the download when memory already holds checkpoint `n == latest` is an optimization the spec marks optional. Not now.
3. **Stale `pending_requests`.** After restore, the handler calls `harness.failStale(now)`. Any entry older than `timeout_s + 60` s is removed and logged as an `error` with `lost: true`, then fed through the same path as a failed response:
   - **REPL:** `rejectPending`, with the message "lost: no response within …". The eval sees a rejected fetch, and a settled eval becomes a tool result.
   - **Model:** the turn ends with the "model call failed" marker.
4. **Delete after checkpoint.** Keep #0013's order: checkpoint first, then delete the held receipts. Add a test that records the order of store writes and deletes, and a test that a failed checkpoint deletes nothing. If messages were deleted without a durable checkpoint, a crash would lose them.
5. **#0013 review note 1, `/clear` with an eval still waiting.** Add `Repl.discard(id)`: the prelude marks the eval `discarded`, and when it settles its result is dropped instead of stored. `/clear` calls it for every open tool call, so nothing leaks into later snapshots. The prelude change affects only new sessions, and no deployed session exists yet.
6. **#0013 review note 2, model id taken before the log write.** `LogWriter.append` accepts `fields` as a function of the seq it actually writes. `model.request` builds its `corr_id` and `body_ref` from that seq, so the id always matches its event.
7. **#0013 review note 3, repeated request ids after a crash.**
   - **Decision:** REPL request ids get a per-run prefix, `repl-<run8>-rN`.
   - **What it means after a crash:** the run that restores re-issues the fetch under a *new* id. Com doesn't dedupe it away, so the request runs twice, which spec §5.4 already allows ("duplicate requests to Com"). The crashed run's late response has an unknown id and is logged and dropped, as the spec says.
   - **Rejected alternative:** reusing the id could deliver the crashed run's response to a re-issued request that isn't the same request, for example when the replayed code reaches `fetch` with a different URL.
   - **Model ids** are already unique because seqs never repeat (note 6).

**Tests** (`checkpoint.test.ts`, MemoryStore with fault injection):
- **Atomicity:** a write fails on the repl snapshot, on a workspace upload or on `latest.json`. In each case the previous checkpoint still restores, and no held message is deleted.
- **Round trip with a pending fetch:** checkpoint with an eval waiting on `fetch`, restore in a fresh handler run, the response settles it, and the workspace files come back.
- **Workspace sync:** only changed files are uploaded, deletes carry over, a local symlink is never uploaded (and the file it points to isn't uploaded through it), keys with `..` are refused on restore, and a stale local file is removed on restore.
- **Stale request:** one stale REPL fetch and one stale model call. The eval gets a "lost" rejection and becomes a tool result; the model turn ends with the failure marker.
- **Delete order:** `deleteMessage` runs after the `latest.json` write.
- **`/clear` with a waiting eval:** after the late response, `__evals` holds nothing for that id.
- **Model id:** a pre-existing log seq forces a conflict, and the id equals the written seq.
- **Crash:** run A sends a fetch and "crashes" without checkpointing. Run B re-sends it under a different id. A's late response is dropped and B's response is used.

# 0025 — Com has no Bedrock (SigV4) auth

| | |
|---|---|

## Description

Com answers every `auth: "bedrock"` request with a terminal `http.response` `{ok: false, error: "bedrock auth not implemented"}` (`functions/com/src/auth.ts`, `UnsupportedAuth`). Spec §6 says `bedrock` signs the request with SigV4 using Com's role, so a Bedrock-configured model provider can't work yet.

## Prerequisites

Probed by planner on 2026-11-21 in `.worktrees/0025-bedrock-auth` at `dd37f4d`.

- [x] **Worktree** `.worktrees/0025-bedrock-auth` on `track-a/0025-bedrock-auth`, with the `.venv`, `functions/node_modules` and `client/node_modules` symlinks in place.
- [x] **The SigV4 signer is already installed**, transitively: `functions/node_modules/@smithy/signature-v4` 5.7.5 (pulled in by the #0024 SDK clients), along with `@smithy/types`. Probe: a throwaway `functions/com/src/` script signed a Bedrock `InvokeModel` request with `SignatureV4({ service: "bedrock", region, credentials, sha256 })`, using a `node:crypto` `Sha256` class with no extra crypto package. It produced `authorization` (`AWS4-HMAC-SHA256 Credential=AKID/20260101/us-west-2/bedrock/…`), `x-amz-date` and `x-amz-content-sha256`. The probe was removed afterwards.
  - **Note:** the `Sha256` class must not use TypeScript parameter properties. Node's type stripping rejects them (`erasableSyntaxOnly`).
- [ ] **The dependency isn't declared.** Relying on a hoisted transitive package is fragile, and declaring it changes the lockfile, which is people-only. Owner issue **#0028** adds `@smithy/signature-v4` to `functions/com/package.json` and re-locks. #0025 can reach `CHECK OK` without it, because esbuild bundles `@smithy/*` (only `@aws-sdk/*` is external).
- [x] **Credentials**: Lambda sets `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` and `AWS_SESSION_TOKEN` for Com's execution role. Read them from the env per request so they're never stale. No credential-provider package is needed.
- [x] **Where auth happens**: `functions/com/src/auth.ts` `applyAuth(req, secrets)` is called from `com.ts` once the request body has been read (`reqBody`). SigV4 needs the body, so the signature grows.
- [x] **Prime has no Bedrock adapter yet** (Track B #0021), so nothing sends `auth: "bedrock"` today. This issue is Com-side only. #0023's live run stays on `mock`.
- **Parallel work:** none in Com. #0009 is in review and only touches `client/`. Don't edit `functions/prime/` or `client/`.

## Plan

Files: `functions/com/src/auth.ts`, `functions/com/src/com.ts` (the call site only), new `functions/com/src/sigv4.ts` + `sigv4.test.ts`, `auth.test.ts`, `stz_agent/stz_agent_stack.py`, `tests/unit/test_stz_agent_stack.py`.

1. **`sigv4.ts`**:
   - `class NodeSha256` implements the `Checksum` shape (`update`, `digest`, `reset`) over `node:crypto`; with a secret it uses HMAC.
   - `regionFromBedrockUrl(url)` parses `bedrock-runtime.<region>.amazonaws.com` (and `bedrock.<region>…`) and throws for any other host.
   - `signBedrock({ method, url, headers, body }, { credentials, now })` → signed headers, via `SignatureV4({ service: "bedrock", region, credentials, sha256: NodeSha256 })`. Pass `hostname`, `path` with the query split out, `query`, and lower-cased headers including `host`. The body is the string or bytes Com sends.
   - `credsFromEnv(env)` returns the three env vars, and throws if the key ID or secret is missing.
2. **`auth.ts`**: change the signature to `applyAuth(req, secrets, body?: string | Uint8Array | null, signer = defaultSigner)`. The `bedrock` case returns `{...headers, ...await signer.sign(...)}` and no longer throws `UnsupportedAuth`. Keep `UnsupportedAuth` exported, since nothing else uses it, but drop it if it's now dead. `com.ts` passes `reqBody`. Never log the signed headers.
3. **IAM** (stack): Com's role gets `bedrock:InvokeModel` and `bedrock:InvokeModelWithResponseStream` on `arn:aws:bedrock:*::foundation-model/*` and `arn:aws:bedrock:<region>:<account>:inference-profile/*`. Cross-region inference profiles fan out to other regions, so the foundation-model ARN uses `*`. Only Com gets it.
4. **Tests**:
   - `sigv4.test.ts`: with fixed credentials and a fixed `now`, the `authorization` header matches a golden string computed once and pinned. It has `Credential=AKID/<date>/us-west-2/bedrock/aws4_request` and a `SignedHeaders` list that includes `host;x-amz-content-sha256;x-amz-date` (plus `x-amz-security-token` when a session token is set). A changed body changes the signature. The region parse accepts both host forms and rejects `api.anthropic.com`. `credsFromEnv` throws when vars are missing.
   - `auth.test.ts`: the bedrock case returns the signed headers and keeps the request headers. The old "bedrock → terminal error" test becomes "bedrock with missing creds → terminal error" in `com.test.ts`.
   - pytest: Com's policy has the two Bedrock actions on those resources, and Prime and Doorman don't.
5. **Verify**: with the usual exports, `scripts/check.sh` → `CHECK OK`, with the new tests counted and `build-functions` bundling `com` with the signer inlined.
6. **Git** (per `Issues.md`): code commits go on the branch; issue-file edits go on `main` only. Stage by path.

## Expected behavior

`auth: "bedrock"` requests are SigV4-signed (service `bedrock`, Com's execution-role credentials, the request's region) and sent like any other request; Com's role gets `bedrock:InvokeModel` on the configured model(s). Tests cover the signed headers with fixed credentials and clock.

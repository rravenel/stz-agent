## Description

`functions/shared/comms-worker.ts` doesn't exist. Prime and Com need it to poll their own queue, ack immediately, keep the per-recipient unacked sets, and run the delivery monitor that sync-wakes a recipient until its ack arrives.

## Long Description

Protocol §4.1, §5, §6:
- Runs in a `worker_threads` worker; implements the interface from #0002 so the in-memory fake and the real worker are interchangeable.
- Long-poll own queue (`WaitTimeSeconds` 1–5 s). On `ack`: clear the unacked entry, delete the message. Otherwise: send `ack` to the sender's queue right away, then hand `(msg, receiptHandle)` to the main thread.
- Delivery monitor: 500 ms tick; `ACK_TIMEOUT` 3 s before the first wake, then `WAKE_ACK_TIMEOUT` per recipient (Prime 15 s, Com 5 s); one wake covers all pending messages; never re-send the message. All timeouts are constructor parameters.
- Sync wake: Lambda `Invoke` `RequestResponse` `{reason:"wake"}`, `maxAttempts: 1`, 2 s abort; classify as `running` (429), `started` (abort), `failed`, `error` and log it. The result never clears an unacked entry.
- Unit tests with an in-memory queue and a fake invoke returning 429/started/failed, covering protocol §9 walkthroughs A–D, using fake timers.

## Plan

Files (all new unless noted): `functions/shared/src/comms-core.ts`, `comms-core.test.ts`, `aws-ports.ts`, `comms-worker.ts`, `comms-worker.test.ts`. Don't touch `functions/prime/` or `spikes/` (Track B).

1. **Ports, so the logic needs no AWS.** In `comms-core.ts`:
   - `QueuePort { receive(waitSeconds: number): Promise<{ body: string; receipt: string }[]>; send(to: Endpoint, msg: Envelope): Promise<void>; delete(receipt: string): Promise<void> }`
   - `WakePort { wake(to: Endpoint): Promise<WakeResult> }` where `WakeResult = { kind: "running" | "started" | "failed" | "error"; detail?: string }`
   - `Logger = (event: { kind: "wake"; to: Endpoint; result: WakeResult } | { kind: "poison"; error: string }) => void`
   - Timeouts in one options object with defaults: `ackTimeoutMs 3000`, `wakeAckTimeoutMs { prime: 15000, com: 5000, doorman: 5000 }`, `tickMs 500`, `pollWaitSeconds 2`.
2. **`DeliveryMonitor`** (pure, time passed in): `track(to, msgId, now)`, `ack(msgId)`, `due(now): Endpoint[]`, `markWoken(to, now)`, `count()`. It implements the protocol §5 pseudocode exactly: per recipient, `waited = now − (lastWakeAt ?? oldest.sentAt)`, `limit = lastWakeAt ? wakeAckTimeout[to] : ackTimeout`; one wake per recipient covers all its messages; `lastWakeAt` resets when that recipient's set empties. The wake result is logged and never clears an entry.
3. **`CommsCore implements Comms`**, which runs in whichever thread owns the ports:
   - Poll loop: `receive` → `parseEnvelope`. A poison message is logged and deleted. For an `ack`, call `monitor.ack(body.acked_msg_id)` and delete it. For anything else, `send(msg.from, makeAck(msg))` **first**, then call the handler with `{msg, receipt}`.
   - `send()` builds the envelope with `makeEnvelope`, calls `port.send`, and tracks it unless the type is `ack`. It returns the envelope synchronously, as the interface requires; the enqueue runs in the background, and a send failure is logged and retried on the next tick.
   - A `setInterval(tickMs)` monitor calls `wake.wake(to)` for each `due` recipient. Never have more than one wake in flight per recipient.
   - `finalPoll(graceMs)`: a single receive with `waitSeconds = ceil(graceMs/1000)`; return true if nothing non-ack arrived. `stop()` clears the interval and ends the loop after the current receive.
   - Doorman can use `CommsCore` directly on its main thread (it has no blocking work). Prime and Com use the worker in step 5.
4. **`aws-ports.ts`** (blocked until the SDK packages land): `SqsQueuePort(urls: Record<Endpoint, string>, self)` uses `ReceiveMessage` (`WaitTimeSeconds`, `MaxNumberOfMessages: 10`), `SendMessage` and `DeleteMessage`. `LambdaWakePort(names: Record<Endpoint, string>, callTimeoutMs = 2000)` does `Invoke` `RequestResponse` with payload `{reason:"wake"}`, `new LambdaClient({ maxAttempts: 1 })` and `abortSignal: AbortSignal.timeout(callTimeoutMs)`. Classify the outcome: abort → `started`; `TooManyRequestsException` / HTTP 429 (check `Reason === "ReservedFunctionConcurrentInvocationLimitExceeded"` when present) → `running`; a returned `FunctionError` → `failed`; anything else → `error`. A normal fast return counts as `started` (the target ran and finished). `fromEnv()` reads the env vars set by #0003: `DOORMAN_QUEUE_URL`, `PRIME_QUEUE_URL`, `COM_QUEUE_URL`, `DOORMAN_FUNCTION_NAME`, `PRIME_FUNCTION_NAME`, `COM_FUNCTION_NAME`. Keep the classifier a pure exported function (`classifyInvoke(err | result)`) so it can be tested without the SDK.
5. **`comms-worker.ts`**: `WorkerComms implements Comms` for the main thread. It spawns `new Worker(fileURLToPath(import.meta.url), { workerData: { self, mode, opts } })`, and the same file runs `CommsCore` with the AWS ports when `!isMainThread && workerData?.stzComms`. Bundles need no `build.mjs` change, because esbuild's single `index.mjs` re-executes itself as the worker. Wire protocol over `postMessage`: main → worker `send | delete | finalPoll | stop | count`; worker → main `delivery | count | finalPoll result | log`. `unackedCount()` must be synchronous, so the worker pushes its count to main on every change and main caches it. `send()` creates the envelope on main (so it can return it) and posts it. `stop()` posts stop, then `worker.terminate()`. A `mode: "memory"` workerData option uses in-worker fake ports, so the test needs no AWS.
6. **Tests** (`node:test`, `mock.timers.enable({ apis: ["setInterval", "setTimeout", "Date"] })`), with a `FakeQueue` (per-endpoint arrays and receipts) and a `FakeWake` that follows a script (e.g. `["running", "started"]`) and records calls:
   - Monitor unit tests: no wake before 3 s; a wake at >3 s; the second wake only after `wakeAckTimeout[to]`; one wake for N pending messages; an ack clears and stops wakes; the message is never re-sent (the queue holds exactly one copy).
   - **Walkthrough A**: Com sends `http.response` and Prime is asleep (no consumer). After 3 s the wake gives `started`; then attach a Prime `CommsCore` on the same fake queue, which acks; Com's `unackedCount()` is 0 and no more wakes follow.
   - **B**: first wake `running` (429); the next wake comes only after 15 s (Prime) and is `started`; then the ack.
   - **C**: the recipient's handler blocks (never resolves), but the ack is still sent before the handler runs and the sender sees count 0 with no wake.
   - **D**: the wake keeps returning `failed`; wakes repeat every `wakeAckTimeout` and are each logged; the message stays in the queue.
   - The receiver acks before handing off, deletes acks, and deletes plus logs poison messages.
   - `classifyInvoke`: abort → started, 429 → running, `FunctionError` → failed, other → error.
   - One `WorkerComms` smoke test in `mode: "memory"` (real timers, short timeouts): send → the delivery reaches the handler → `stop()` resolves.
7. **Verify**: with the usual exports (`PATH` with Node 22.21.1, `PYENV_VERSION=system`, `JSII_RUNTIME_PACKAGE_CACHE_ROOT=$PWD/.logs/jsii-cache`), `scripts/check.sh` → `CHECK OK`, with the walkthrough tests named `walkthrough A…D` in the `test-functions` output. If the SDK packages haven't landed yet, ship steps 1–3, 5 and 6 with `aws-ports.ts` limited to the pure `classifyInvoke` plus a TODO, and record that in `## Fix`. Don't stub SDK types by hand.

## Description

`scripts/setup.sh`, `build.sh`, `test.sh` and `deploy.sh` are scripted, but the versions they run with float, so two machines (or two days) can build, test and deploy different things:

1. **Python deps are ranges.** `requirements.txt` has `aws-cdk-lib>=2.277.0,<3.0.0` and `constructs>=10.5.0,<11.0.0`; transitive deps (jsii, cattrs, …) are unpinned. There is no lock file or hashes.
2. **npm deps have no lockfile.** `functions/package-lock.json` doesn't exist, so `setup.sh` falls back to `npm install` and resolves fresh versions each run (`esbuild ^0.28`, `typescript ^7`, `@types/node ^22`).
3. **The CDK CLI floats.** `deploy.sh` uses whatever `cdk` is on `PATH`, else `npx --yes aws-cdk@2` (latest 2.x at deploy time).
4. **The toolchain isn't pinned.** No `.python-version` or `.nvmrc`. `setup.sh` falls back to any `python3` (3.15 on this machine) when `python3.12` is missing. The Lambda bundles target `node22`, but local Node can be any version `>=22.18`.

## Expected behavior

A clean checkout plus `scripts/setup.sh` gives the same Python packages, npm packages and CDK CLI on every machine, verified by hashes or lockfile integrity. Setup fails clearly when the required interpreter is missing rather than silently using another one.

## Resolution notes

> 🟢 Resolved 2026-11-20 — setup installs from a hashed Python lock and `npm ci`, the CDK CLI is pinned, and Python 3.12 is enforced.

Independent review (Opus) re-ran `scripts/check.sh` (`CHECK OK`, pytest 1, test-functions 21) and a fresh clone run from cwd `/` (setup + check OK, `pip freeze` equals the lock, re-compiling gives a byte-identical lock). Minor follow-ups it noted, none blocking:
- `setup.sh`: `uv python find` can return a venv; `--system` would be cleaner.
- `setup.sh`: `pip install --no-deps` leaves packages dropped from the lock in an existing venv (`uv pip sync` or rebuilding the venv would fix it).
- `.python-version` with a patch version (`3.12.15`) would break the major.minor check.
- `lock.sh` ignores unknown arguments.
- `README.md` "Daily use" still mentions a bare `cdk deploy -c env=demo`.

## Root cause

Dependencies were declared with ranges and no lock files, the CDK CLI came from `PATH` or `npx aws-cdk@2`, and the interpreter was "whatever `python3` is". Also, `deploy.sh` didn't activate the venv, so `cdk.json`'s `python3 app.py` ran under the system Python.

## Fix

- `requirements.lock`, generated by `uv pip compile --universal --generate-hashes --python-version 3.12`. `setup.sh` installs it with `pip --require-hashes --no-deps`, so consumers need only pip, not uv.
- `functions/package-lock.json` is committed. `setup.sh` runs only `npm ci` and fails if a lockfile is missing.
- `aws-cdk` is pinned to exactly `2.1149.0` as a `functions/` devDependency. `deploy.sh` uses `functions/node_modules/.bin/cdk` with `--app ".venv/bin/python app.py"`.
- `.python-version` (3.12) is enforced. `setup.sh` finds `python3.12` or uv's 3.12, never another version, and rebuilds a venv made with a different version. `venv_python` (used by build, test and deploy) refuses a wrong-version venv.
- `.nvmrc` pins Node 22, but a mismatch is only a warning.
- New `scripts/lock.sh [--upgrade]` re-resolves both lock files, then runs setup.
- esbuild's postinstall is denied in `allowScripts`. npm 11 already skips unapproved scripts, and esbuild works without it.
- The `I1` milestone is added to `project.json`'s grouping pattern and to `Issues.md`. `next-issue.py I` already worked.

## Decisions taken without the owner

- **Node is warned, not enforced.** Bundles are fixed by esbuild's `target: "node22"` and the locked esbuild, and local machines run Node 26. Enforcing would break every current setup. Would change if a test passes or fails differently across Node majors.
- **The CDK CLI lives in `functions/`' devDependencies** rather than a new root `package.json`. It reuses the existing lockfile and `npm ci` step. **Wants owner feedback:** Track A owns `functions/package.json`, so confirm they're fine hosting the CLI there.
- **`.nvmrc` is 22**, matching `engines` and the bundle target, even though the README said "24 recommended". The Lambda runtime choice is Track A's.

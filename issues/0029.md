## Description

When a message reaches Prime's queue just after the 1 s stale-wake window, Prime exits `stale_wake` and the message is left received but not deleted. It stays invisible for the queue's 900 s visibility timeout, and nothing wakes Prime again, so the turn hangs. Found running the #0008 run-book (`scripts/e2e.ts`) on `StzAgent-brennan`. It blocks #0023.

## Steps to reproduce

1. `STZ_API_TOKEN=… scripts/deploy.sh` (default mock model), then `node scripts/e2e.ts --env <you>`.
2. The script sends `POST /wake`, then `POST /messages` straight after.

## Expected behavior

Prime processes the message: either in the run that the prewake started, or in a new run started by Doorman's message wake.

## Actual behavior

Observed 2026-11-21 (UTC):

- 02:40:53: `POST /wake → 202 {"wake":"started"}`, then `POST /messages (try 1) → 202`.
- 02:40:55–57: Prime's only run (2 GB, 1.6 s). It logs `{"event":"stale_wake","reason":"prewake","waited_ms":1000}` and exits.
- After that, Com never runs and Prime never runs again. The `GET /events` timeline has only the `stale_wake` event. The e2e script was stopped by hand after about 5 minutes with no further events.
- Prime queue: `ApproximateNumberOfMessages 0`, `ApproximateNumberOfMessagesNotVisible 1`, `VisibilityTimeout 900`.

## Notes (likely root cause)

- `functions/prime/src/handler.ts:84-94`: the stale-wake check waits `staleWakeMs` (1 s) for `inbox`. If the inbox is empty, it returns, and the `finally` calls `comms.stop()`.
- `functions/shared/src/comms-core.ts:183-187`: `stop()` sets `stopped` but then awaits `this.polling`, the in-flight long poll (`pollWaitSeconds: 2`). If the message arrives during that poll, `pollOnce` → `handle` delivers it to `onMessage`, into an `inbox` the handler has already abandoned. Nobody deletes it or releases it.
- Doorman's wake for the message is sent while Prime is still in that run (reserved concurrency 1), so it reports `running` and starts nothing. No later wake comes.

Possible fixes (for the planner to choose):

1. **On stop, return undelivered work.** In `comms-core` / `comms-worker`, a message received after `stop()` began, or one handed to `onMessage` but never deleted, gets `ChangeMessageVisibility 0`, so it's visible again immediately. This needs a `release(receipt)` op on the queue port (and its fake).
2. **Re-check after stop in the stale-wake path.** Stop comms first, then check `inbox` again. If a message landed, release it, or carry on to restore instead of returning `stale_wake`.
3. **Belt and braces:** a non-empty inbox at any exit is a bug. Release everything that's left in the `finally`.

A unit test with the comms fake should reproduce it: deliver a message during the final in-flight poll after the stale-wake window closes, then assert it's visible again or processed.

Also worth checking: the same strand can happen at `exit_idle`, if a message arrives during the `stop()` after `finalPoll` returns empty.


## Plan

Planned and built by Elliot on 2026-11-21. P0; it blocks #0023.

- **Why releasing the message isn't enough:** the message from the worker's last poll has already been **acked** (`comms-core.handle` acks before it hands the message over). Doorman's delivery monitor therefore stops waking Prime. Releasing it (option 1, visibility 0) would make it visible, but nothing would wake Prime to read it. So the fix is for Prime to process it.
- **Prime-side fix** (options 2 and 3, all exit paths): stop comms *before* the exit decision. If the inbox isn't empty after `stop()`, restart comms and keep going in the same run.
- **No change to Track A's `comms-core.ts`**, so decision (a) isn't needed for this bug. A `release` op is still worth adding later for crash paths. It's up to Rene.

## Root cause

`stop()` awaits the worker's in-flight long poll. A message that poll receives is acked and delivered into an inbox that the run had already stopped reading. It happened at the stale-wake exit (seen live on `StzAgent-brennan`), and could happen just the same at `exit_idle` and `exit_deadline`. The sender sees the ack, so it sends no further wake. The message stays invisible for 900 s, and the turn hangs.

## Fix

Branch `track-b/0029-stranded-message`, commit `7550755`, in `functions/prime/src/handler.ts`.

- **`RunComms`:** a restartable wrapper around `deps.comms()`. `stop()` is idempotent, because a `WorkerComms` can't be stopped twice. `restart()` makes a new worker and re-registers the inbox handler. Receipts belong to the queue, so the new worker deletes the earlier worker's messages.
- **Stale wake:** with an empty inbox after the wait, Prime stops comms. If a message arrived meanwhile, it restarts comms and restores as normal instead of returning `stale_wake`.
- **`exit_idle` and `exit_deadline`:** after the final poll, or before the self-wake, Prime stops comms. If anything arrived, it restarts and goes back round the checklist, with another checkpoint and the deletes. The self-wake is still the last action.
- **After the run deadline,** inbound messages are now absorbed until exit. The old cut-off (hard stop − 60 s) left them in SQS, which caused the same strand (#0016 review note 1).
- **Remaining case:** a run that throws can still leave messages invisible. That's the designed crash path (spec §5.4), but there's no wake afterwards. A `release` in `comms-core` plus a wake would close it; it's left for Track A.
